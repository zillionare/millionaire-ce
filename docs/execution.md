# 成交时序与策略防呆

策略作者需要明确什么时候形成信号、什么时候允许成交，以及下单时哪些数据已经可得。
框架负责执行固定周期和交易条件，策略通过标准 Broker 接口表达买卖意图。

## 周期是策略的固有属性

新策略显式声明 `BAR_INTERVAL = "1d"` 或 `BAR_INTERVAL = "30m"`。
运行器会检查策略声明、运行周期以及 `bar_interval` 配置是否一致。
日线策略不能在启动时换成 30 分钟，反过来也一样。

例如，`MLMomentumReversalStrategy` 是日线，`LightGBM30mSmokeStrategy` 是 30 分钟。
后者是生命周期验证示例，不是把前者切换一个参数得到的分钟版。
如要研究另一个周期，应创建新的策略类，重新选择因子窗口、训练标签和验证样本。

这一约定让策略只处理自身的一种节奏，不必为任意运行时周期分支编写逻辑，
也避免把“20 日均线”误执行成“20 根 30 分钟线”。

## 两种常用成交模型

| 模型 | 回测中的含义 | 仿真中的对应行为 |
| --- | --- | --- |
| cheat-on-close / `auction_close` | 用本 bar 数据形成信号，按同一 bar 的收盘模型撮合 | 收盘前用当时可见行情计算并提交，日线默认关注 14:57 起的收盘集合竞价窗口 |
| 显式 `fill_timing="next_open"` | 在信号 bar 结束后保留意图，于下一 bar 开盘模型执行 | 通过持久化意图队列等待下一可交易时段，覆盖午休和跨交易日 |

日线收盘模型示意：

```text
回测：T 日历史 bar（含最终 close） → 计算信号 → 按 T 日 close 模型成交
仿真：T 日收盘前可见行情        → 计算信号 → 提交委托 → 等待可执行行情
```

cheat-on-close 是一个明确的建模假设。最终收盘价事前并不可知，实盘排队成交也无法
保证；因此不能用此模型证明策略可以提前知道收盘价或保证按该价格成交。
模型训练标签只能用于已完成训练样本，不能成为决策时的输入特征。

新策略建议明确设置 `fill_timing`，不要依赖旧策略未声明时的兼容行为。
`cheat_on_close` 是已有兼容配置；ML 日线示例默认 `auction_close`。
30 分钟收盘信号使用对应 bar 的窗口，不能套用日线的 14:57 时刻。

## 框架检查什么

- **T+1 与可用持仓**：当日买入股份不能当日卖出；可用数量与总持仓分开保存。
- **资金与数量**：可用现金、委托数量、费用和买入整手约束由交易路径校验。
- **涨跌停撮合**：采用保守的涨停买入/跌停卖出限制，不以历史最高最低价假装获得排队成交。
- **周期冲突**：启动前拒绝与策略固有周期不一致的配置。
- **提交与恢复**：通过稳定订单意图标识和对账减少重试导致的重复下单。

停牌时可以仍有原持仓，但不应凭空产生正常成交。未成交、部分成交、拒单和撤单是
不同状态，不能把下单返回理解为全部成交。

## 当前边界

这些规则需要正确的行情、涨跌停价和交易日历。当前 Paper 和独立模拟柜台在缺少
有效涨跌停信息时仍有跳过该项限制的路径；自定义数据/柜台接入必须验证该情形，
本版不作“不可能绕过交易规则”的绝对承诺。

本页的防呆是标准执行路径的合同，也不代表框架已实现对任意 Python 策略的通用审计。
未来扰动、随机对照和变异测试属于[下一版规划](roadmap.md)。
