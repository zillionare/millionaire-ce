# 最终用户文档规划（讨论稿）

目标：新用户能够独立完成安装、初始化、第一次回测、查看结果和启动仿真；
策略开发者能够复用示例的训练、调参、解释与执行流程，集中编写和验证因子。
当前手册仍有缺口，本文件是后续编写和验收依据，不代表这些教程已完成。

## 产品主线与表述边界

建议首页定位：**面向 A 股、让策略从研究走向持续运行的开源量化框架**。

| 核心能力 | 用户获得的价值 | 文档需要说明的边界 |
| --- | --- | --- |
| 统一策略与 Broker 接口 | 同一策略复用到回测、仿真和 HTTP 柜台适配器，减少执行模式切换时的重写。 | CE 仅提供独立模拟柜台验证第三条路径，不开放真实交易；真实柜台由 Millionaire 或其他宿主扩展装配和验收。接口一致不等于成交价格、延迟或收益完全相同。 |
| HTTP 交易柜台接口 | 用户可以自行实现券商柜台适配；不熟悉编程的用户也能借助 AI，依据协议、示例和验收用例生成适配器，复用策略执行链路。 | 适配结果仍须验证订单状态、幂等和错误语义；CE 只提供本机 HTTP 模拟柜台作为参考，不开放真实交易。 |
| 统一行情数据与 adapter | 策略使用统一数据结构，数据供应商差异由适配层处理。 | 必须公开字段、证券编码、交易所时区、复权、单位、已完成/形成中 bar 的含义，以及供应商周期、市场和权限覆盖；结构统一不代表缺失数据自动得到补全。 |
| 明确的成交时序 | 显式选择 cheat-on-close、next-open 等模型，理解信号与成交的先后关系。 | 回测用最终收盘数据计算并按同一收盘价成交是一种建模假设；仿真在收盘前只能使用当时可见信息，最终收盘价和排队成交无法保证。日线与 30 分钟分别配时序示例。 |
| 框架执行 A 股交易规则 | 标准交易接口下，由 Broker/撮合层统一检查 T+1、可用仓位、资金、涨跌停等条件，减少策略遗漏。 | 不使用“不可能绕过”作为当前承诺。`PaperBroker._reject_at_limit` 在价格或有效限价缺失时存在跳过检查的路径，`SimulatedCounter._executable` 在限价缺失时使用无限/零边界；需要补齐规则数据缺失处理及回归，再声明其具体保证。涨停买入/跌停卖出的保守撮合规则也应公开。 |
| 策略周期是固有属性 | 策略声明日线或 30 分钟周期，运行器拒绝不匹配的周期和配置覆盖；编写策略时无需兼容任意周期。 | 要改变周期应创建并验证新的策略类，不能把运行表单中的周期切换视为策略转换。 |
| LightGBM、参数优化与预测解释 | 示例提供选股、训练、调仓、调参和预测解释的可复用流程，用户优先研究因子。 | 当前因子选择依赖固定 catalog，自定义因子须说明计算、登记、选择、标准化和解释的接入步骤；不承诺任意因子函数自动插入。SHAP 解释预测贡献，不等于已实现组合收益或因果归因。 |

文档应把每个卖点写成“用户问题 → 系统如何解决 → 可运行示例 → 支持边界”。
首页优先突出统一策略路径、交易规则和因子研究流程；HTTP、adapter 与数据格式在对应
章节进一步解释其价值，不用未经验证的竞品优劣比较支撑卖点。

## 推荐阅读路径

用户主路径：了解能力 → 安装 → wizard/数据准备 → 首次回测 → 阅读报告 → 仿真 → 日常维护。

策略开发路径：运行 LightGBM 示例 → 选择已有因子 → 添加自定义因子 → 参数优化 →
解释单次预测 → 回测和仿真验证。普通用户不必先阅读 SDK 或内部设计。

| 章节 | 最小交付内容 |
| --- | --- |
| 首页与能力边界 | 核心价值、CE 与宿主边界、支持平台（macOS ARM64 / Ubuntu x86_64 / Windows x64）、明确的快速开始入口。 |
| 下载与安装 | 版本对应的真实 Release 下载链接、SHA-256 校验、三平台安装和控制器、签名提示、升级、卸载及保留数据行为。 |
| 初始化与数据 | wizard 步骤、Tushare token/权限、证券与日历、周期/市场覆盖、下载进度与失败重试、首次可用数据的判断。 |
| 行情与数据约定 | 统一 schema、adapter 边界、复权与单位、闭合/形成中 bar、缺失数据处理；腾讯默认关闭、一次 30 天演示且不能续开，到期接入扩展。 |
| 第一次回测与报告 | 固定示例、资金/周期/日期/费用/时序设置、完成标志、收益/回撤/交易/失败原因、结果持久化和重开。 |
| 成交时序与交易规则 | 日线/30 分钟的信号时间轴，cheat-on-close 与 next-open 对照；涨跌停、T+1、资金和仓位规则、部分成交/撤单，以及数据不足时行为。 |
| 仿真与一致性 | 复用回测策略和配置、启停与恢复、差异排查；独立 HTTP 模拟柜台验证入口及其能力边界。 |
| 因子与 LightGBM 策略 | 先运行原版，再增添一个最小因子；明确输入输出、预热窗口、缺失值、可用时间、训练标签、因子登记和缓存版本。无需重写训练和下单流程的部分须实际验证。 |
| 参数优化 | 网格/随机搜索、搜索范围、样本内外切分、目标指标、随机种子、算力预算、优化结果重新回测及过拟合判断。 |
| 预测解释与策略分析 | 单资产单决策日的 SHAP、因子取值、模型/配置与时间点复现；分别说明预测贡献、交易表现和未来可能的收益归因。 |
| 运维与故障处理 | 服务控制、日志与任务状态、备份/恢复、端口冲突、权限/token/数据缺口、异常重启和版本升级；公开系统重启/断电及长期运行的验证边界。 |
| 开发者参考 | 策略/Broker/行情扩展契约、HTTP 模拟柜台、质量门禁与贡献说明。内部设计单独导航并标注设计/历史状态。 |

用户指南统一使用中文；API、配置键和代码保留原名。导航与搜索需匹配中文内容。
README 作为用户入口，源码安装放到开发者路径。清理首页、scope 和设计页中与当前实现
矛盾的旧说明，不将尚未实现的设计当成产品能力。

## 编写顺序与发布验收

1. 先修正现有支持范围与旧描述，再完成安装、wizard、首次回测和仿真的主路径。
2. 用同一个 LightGBM 示例贯穿因子接入、调参、预测解释，避免多套互不兼容的教程。
3. 补齐运维/故障处理、数据契约、SDK 参考，并整理中文导航与搜索。
4. 对代码尚不满足的表述先明确限制；需要代码保证的能力单独修复并验证，不能靠文档承诺。

正式发布的最低验收：

- 三个支持平台按实际 Release 包验证文档中的安装、启动、升级、卸载步骤。
- 使用新配置和明确的数据/token 前提，照教程完成初始化、首次回测、报告重开与仿真启停。
- 自定义因子示例实际参与模型输入、参数优化和 SHAP 展示；对相同配置可复现实验。
- 每条突出能力都有可运行示例或验收证据，并准确注明模拟/真实、已验证/未验证边界。
- 文档命令、配置键、链接和 UI 名称与交付版本一致；不把 CI artifact 当成已发布 Release。
- MkDocs strict 构建通过，用户主路径无占位页、失效入口或误导性的旧设计指令。

通过以上验收后，才能将手册标为“适合最终用户正式发布”；文档站点能构建不是充分条件。
